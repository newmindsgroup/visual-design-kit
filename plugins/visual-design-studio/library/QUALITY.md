# Quality and acceptance boundaries

Version-Timestamp: 2026-09-10 19:58:10 AST

1. Machine structure: run the applicable CLI validators. Errors are blocking for structural acceptance; a pass validates only the implemented contract. Remote URLs are recorded and never fetched.
2. Evidence and content: confirm source authority, freshness, conflicts, rights and claim accuracy with authoritative evidence. A local hash proves byte identity, not truth or legal permission.
3. Creative and accessibility: review the rendered result against the intended audience, brief and medium. Use actual contrast/interaction and desktop/mobile checks when applicable.
4. Users and destination: use real participant/device/runtime evidence for usability, reach, playback, manufacturing or deployment claims. Synthetic records prove none of these.
5. Independent review: substantive implementation and consequential deliverables require the project-approved independent review. Saved subscription billing settings alone do not authorize sharing confidential material externally.

A completion report names each applicable gate and its actual result, evidence and unresolved owner/action. Machine checks and a local code review do not replace independent review. No review result or production approval is inherited from the library authoring project.

Use only commands listed in the assembled package test manifest and [usage guide](USAGE.md). Verify the destination Python version and required files before running them. A command mentioned in source history is not automatically bundled. Record actual exit status and evidence. Runtime compatibility and independent review remain unverified until performed for this package and intended use.
