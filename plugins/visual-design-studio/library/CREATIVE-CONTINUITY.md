# From visual rules to dependable revisions

Version-Timestamp: 2026-09-09 10:37:21 AST

This extends existing identity, handoff, production and delivery ownership. It defines repeatable procedures; it does not claim successful generated characters, cross-channel tests or audience research until actual artifacts have been inspected.

## Character and visual-family consistency

Freeze a project-approved reference sheet and invariant list before the consistency exercise. For a fictional test, use an explicitly test-only accepted baseline, not fabricated client approval. Select representative pose/view/expression/scene variations and at least one difficult interaction; use a bounded set before batch production. Keep identity fixed while varying one intended factor where useful for diagnosis.

Save every first output and its reference IDs, model/tool version and settings when available. Compare silhouette, proportions, face/features, distinctive marks, costume, material, palette, line/shading style, anatomy where applicable and relationships with other characters/props. Record intended variation separately from drift. A beautiful but inconsistent image fails identity preservation. A consistent but unreadable or irrelevant image also fails its purpose.

Reject or repair the actual candidate using appropriate existing tools: constrained edit, vector component, reference-conditioned generation or manual native editing. Before any provider-based reference use, link the recorded Production-access check in AI-DESIGN-CONTEXT.md: relevant operations, terms, rights/likeness permission, authorized data destination and cost. Missing required authorization holds that operation; use an authorized local alternative when suitable. Reinspect repaired outputs and one sibling for unintended family drift. Tool/provider/model changes trigger a new bounded comparison. No seed-based guarantee or global quality score substitutes for this evidence.

## One direction across multiple channels

Use the same approved message and visual-language baseline for a small set of applicable formats, such as a web opening, an ad and a physical display. Record per-channel audience context, viewing distance/time, size, hierarchy, interaction, safe regions, copy limits and actual acceptance conditions. These are not merely resized crops.

Identify invariants (recognition, message, canonical values, character identity) and permitted adaptations (composition, crop, density, motion and channel-specific typography). Inspect each at its intended size and difficult context. Carry brand consistency and channel usefulness as separate criteria; neither can cancel the other. Physical-device and audience checks remain pending until performed.

## Client feedback to precise revisions

Capture each comment verbatim with author, date and referenced candidate. Translate it into an actionable hypothesis, affected artifact/family IDs, requested change and intended outcome. For example, “warmer” might concern color, photography, language or spacing. Use context to propose a concrete interpretation and ask only if alternative interpretations materially change the result.

Classify: factual correction, usability issue, brand mismatch, preference, new scope or unresolved conflict. New scope requires authorization recorded in design-work before dependent execution; route a changed direction through reference-direction only when that choice is actually reopened. Prioritize factual, task, accessibility and approved-brand requirements; do not let aesthetic preferences erase them. Identify the authorized decision owner and resolve contradictory feedback there. Consolidate comments without hiding disagreement or treating a majority vote as authority.

Create a revision packet with the exact baseline/version, approved change scope, preserved invariants, affected outputs and checks. Produce a separate candidate; compare before/after using the same content/context where possible. Record each comment as addressed, clarified, deferred with owner, rejected with rationale or superseded. Only actual approval updates the accepted baseline. Reopen affected tests after changes; preserve unrelated approved decisions.

## Retrieve and retire the right assets

Extend the existing project asset/manifest record with family/asset ID, variant, intended channel, master/source version, approval evidence, rights/expiry, status and replaced-by reference when needed. Do not build a competing asset database. Use these conceptual labels in the existing work/asset record, without adding undeclared fields to a strict manifest schema: draft has no asset approval; test-only is restricted to the named exercise; accepted-for-scope requires actual approving-party evidence for that asset/version and intended use in design-work; superseded is excluded from new production selection. Direction approval does not automatically approve every asset. Campaign-to-permanent promotion follows the visual-language template and requires an explicit new owner decision. Retrieval must check intended use and approval, not filename similarity or last-modified time.

When an asset changes, identify dependent compositions, templates and exports. Mark affected results stale and regenerate only authorized outputs. Preserve historical evidence and superseded files for traceability; exclude superseded variants from new production selection. An asset approval does not override a license expiry or authorize a different likeness/use.

## Learn without spreading client information

Capture a reusable lesson only as an original general rule with its evidence limits. Keep client assets, private critique and brand values in the client workspace. A successful fixture is a narrow example, not a mandatory design default. Use failures to improve the existing guide rather than install another overlapping skill.
