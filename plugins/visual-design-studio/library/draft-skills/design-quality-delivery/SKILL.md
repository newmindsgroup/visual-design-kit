# Delivery

Version-Timestamp: 2026-09-10T20:53:18.553556-04:00

Project-local instruction draft. Manual selection does not install a tool or grant permissions.

## Inputs

Requirements, evidence and selected actor/persona references under the [shared rule](../../CAPABILITY-CONTRACTS.md#audience-input-selection), candidate and baseline, manifest, output specifications and actual check results. Reuse valid existing prerequisites; missing audience research follows the shared rule's hold or specifically authorized provisional-exploration branch, never a self-declared exception.

## Method

Follow [delivery preflight](../../DELIVERY-PREFLIGHT.md) for candidate identity, native reopen, export inspection, package reconciliation and correction/recheck. Keep results in the existing work record and manifest. Verify the actual destination route and applicable saved evidence before claiming an app-specific delivery. Historical host readiness does not transfer to another project or machine.

Run the deterministic validators for applicable records and compare declared structured invariants. Review the rendered artifact against the brief, content accuracy, accessibility and medium requirements. Record each criterion, method, result and evidence. Keep structural pass, creative review, factual/legal review, usability and native/device acceptance separate. Investigate failed checks and document any exception with its owner; no exception implies approval. Verify editable source, exports, dependency/license notes and recovery instructions. Prepare delivery without sending or publishing unless authorized. Include refresh triggers and ownership so the next session can inspect current files before resuming.

## Output contract

Fill [design work](../../templates/design-work.md), selecting the sections relevant to this capability. Include: QA matrix, validation report references, manifest, limitations, recipient checklist, maintenance triggers and resumable stage handoff. Refer to stable IDs and paths rather than pasting full research or personas.

## Acceptance

Verify the recorded audience selection, rationale, evidence limits and named use under the shared audience input rule. Reassess affected audience inputs on scope, evidence or intended-use changes; preserve historical results and hold dependent use until required conditions are resolved. Audience records alone never prove usability or production acceptance.

Required failures prevent completion claims; independent review status is explicit; no unsupported production acceptance; delivery boundary follows user authorization. Apply [quality boundaries](../../QUALITY.md). Unsupported checks remain pending with an owner and next action. For a revision, load [stage handoff](../design-stage-handoff/SKILL.md) and compare only the authorized delta.

## Example and evidence discipline

Classify each criterion in the work record as a normative standard, platform guidance, project requirement or heuristic. Check the applicable version, level and exceptions before adopting numbers. For a specimen, verify its stated representation and actual transitions; a static state illustration or conformance badge is not behavior evidence.


## Video-informed method acceptance

When checking a video-informed change, distinguish captured source, inspected file, authored method and tested behavior using [video intake](../../VIDEO-INTAKE.md). A private-community landing page is not the promised resource. For selected motion work, check the relevant [recipe acceptance](../../MOTION-RECIPES.md) against actual playback/exports. Use existing voice and content checks for copy; a style-pattern score cannot verify facts, conversion, human authorship or untested languages. Report pending access and runtime evidence explicitly.



## Visual craft evidence

Apply [craft review](../../DESIGN-CRAFT.md) to selected visual deliverables. Source/code checks alone do not prove visual quality. Preserve font-file/role evidence, color-combination results and motion fallback/target checks through their referenced records. A common visual style is not automatically defective; explain the actual failure and proposed correction.
